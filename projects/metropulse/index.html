DATA ARCHITECTURE · ANALYTICS · AI

MetroPulse

A Serverless Incremental Lakehouse Reference Architecture

An end-to-end reference implementation built to explore a deceptively difficult architecture question: how do we turn operational business events into trusted, governed analytical information — and then make that information accessible through both deterministic software and natural-language exploration?

Architecture Lakehouse / Medallion
Platform Databricks + AWS
Source PostgreSQL business events
Consumption Dashboard · App · Conversational AI
Primary concern Architecture decisions, not product features

THE PROJECT

The system is the experiment.

MetroPulse models a ride-share operation, but the transportation domain is intentionally secondary. The project exists to examine architectural responsibilities that recur across transactional, financial, claims, tax, IoT, and other event-oriented systems.

Rather than beginning with Databricks features and looking for places to use them, the implementation begins with system responsibilities: protect the operational workload, preserve source evidence, reconstruct trustworthy analytical state, expose stable business models, govern access, and support different forms of consumption.

Architecture principle

Design the logical architecture around durable responsibilities and change. Design the physical architecture around requirements that actually exist.

01

THE PROBLEM

Operational data is not automatically an analytical system.

01

Protect operations

PostgreSQL represents the operational system of record. Analytical scans, historical reconstruction, aggregation, dashboards, and AI workloads should not compete with the workload responsible for running the business.

02

Preserve evidence

Business events need a durable, source-faithful landing point so downstream systems can be replayed, repaired, and evolved without repeatedly coupling themselves to the operational database.

03

Establish trust

Arrival order is not necessarily business order. Duplicate, late, malformed, and contradictory events require explicit treatment before the data becomes a trusted analytical representation.

04

Support different questions

Executives need stable metrics. Investigators need detailed state and history. Analysts need flexible exploration. Natural-language users need governed context rather than unrestricted access to raw data.

02

ARCHITECTURE

A chain of responsibilities — not a chain of product logos.

Each boundary exists because the information has acquired a different responsibility. The implementation happens to use PostgreSQL, AWS, and Databricks; the architectural decomposition is more durable than those individual technology choices.

OPERATE PostgreSQL System of record
→
PRESERVE S3 Source-faithful events
→
INGEST Bronze Raw analytical representation
→
TRUST Silver Validated state + history
→
MODEL Gold Business consumption
→
CONSUME Experiences Dashboard · App · AI
S3 Original Source

It decouples extraction from downstream processing and provides replayability, source fidelity, and failure isolation.

Bronze Intentionally imperfect.

It records what the analytical platform successfully received rather than silently rewriting source evidence.

Silver Establish analytical trust.

Quality rules, deduplication, business-time sequencing, current state, and historical state belong here.

Gold Express business purpose.

A Gold model does not have to be aggregated; its defining property is a stable business-consumption grain.

Durable architecture

Operational system → durable source-faithful events → raw analytical representation → trusted analytical representation → business-consumption models → governed deterministic and exploratory consumers.
